# Backup safety and semantics

## Snapshot protocol

1. Resolve source paths and target volume identities. Scan selected entries, metadata and SHA-256 content hashes; fail on unreadable or unsupported special files.
2. Compare against each target's latest complete snapshot. Invoke a real rsync `--dry-run` with the same NUL-delimited manifest and transfer options. The UI shows changes and estimated logical transfer bytes. Preview is informative; execution rescans current source data instead of trusting a stale preview.
3. Create `<target>/LocalBackup/plans/<plan-id>/staging/<snapshot-id>`. Check estimated transfer size against available disk space with a safety margin. This estimate is conservative, not a reservation.
4. For each enabled source, run rsync to its independent `<source-id>` subtree. `--checksum --link-dest` receives a curated reference tree containing only entries whose preserved metadata matches the new scan and the actual old file; changed metadata is never offered as a link candidate. This also works around system openrsync versions that incorrectly reuse files with different permissions. No `--inplace`, no target delete, no shell interpolation.
5. Renamed/moved regular files can reuse a verified old inode only within the same source. Require matching full content hash, size, mode, second-resolution mtime and extended-attribute fingerprint, then re-read and verify the old content and attributes before linking. Changed metadata/content falls back to copying. This is safe reuse, not a promise to avoid reading large files.
6. Verify each listed destination entry against its source scan hash or symlink target. With rsync 3.x, also verify extended attributes. fsync files, manifest and directories, then atomically rename staging into snapshots and fsync the containing directory.
7. Persist the completed snapshot and update file indexes. A full plan run succeeds only after all enabled sources and all enabled targets finish. Manual source-scoped runs update the selected sources and retain the other sources from each target’s previous snapshot; mount-triggered runs execute only their bound destination scope. If one target fails after another has committed, the first target's independent complete snapshot remains valid, while the overall run is failed.

There is no source point-in-time filesystem snapshot. Concurrent file changes that differ from the scan cause verification failure; entries created after scanning may appear only in the next run. Close/export databases, virtual machines and similar application data before backup.

The source root itself is a container; its mode/mtime is not restored. Basic mode preserves file contents, file permissions, modification times and symbolic links. ACLs, ownership, birthtimes, Finder flags and original hardlink relationships are not guaranteed. System openrsync does not preserve all extended metadata; rsync 3.x adds `-X`. The staging filesystem is probed for case/Unicode/name-normalization aliases and colliding paths are rejected before transfer. Other filesystem incompatibilities fail before publication or via verification, rather than being silently marked successful.

## Deletion, retention and recovery

A source deletion omits that file from the new snapshot only. Prior snapshots remain unchanged. Mirror mode can remove in-scope paths from its atomic current view only with a fresh, explicitly confirmed deletion preview. Incremental current views retain missing paths. Both preserve committed history; see backup-modes.md.

Retention is previewed and explicitly applied by the user. It removes snapshots exceeding either keepLast or keepDays. Every destination's latest snapshot, current-pointer generation and all pinned snapshots are protected. Optional daily/weekly/monthly tiers additionally protect the newest snapshot in each of the last N populated UTC calendar periods (ISO weeks start Monday); tiers are combined by union and evaluated independently per destination. Apply rechecks the current policy before accepting previewed IDs. Pin changes are blocked while file tasks run. Logical file sizes cannot be summed to infer physical allocation because snapshots share hardlinks.

Interrupted/failed staging directories are never shown as successful. Startup marks unfinished runs recoverable, then reconciles orphaned committed manifests for configured targets. Compatible complete files from interrupted staging can be verified and reused into a fresh staging tree; partial files are not resumed. Re-run the plan to produce a new complete snapshot. See staging-recovery.md for receipt validation and reuse conditions.

If the database is lost, start with a fresh data directory, then Settings → rediscover history → select the parent target directory containing LocalBackup. The service verifies manifest identity and file hashes, imports complete snapshots and supports restore without the original plan. Current manifests carry full plan configuration and external pin markers. Reviewed recovery can rebuild paused plans, rules, schedule configuration, target bindings, historical indexes and pins; it never automatically resumes scheduling. Legacy manifests without configuration cannot reconstruct plans. Run logs, local jobs, settings and schedule runtime checkpoints are not reconstructed. See configuration-recovery.md.

Restore uses a new randomly named LocalBackup-Restore directory under a chosen existing directory, outside source directories and configured backup roots. It never overwrites the original source. The restore transfer is allowlisted by the selected manifest, with no recursive discovery of untracked files. Listed file types, content and symlink targets are checked before transfer; content, types, permissions, file times and available extended metadata are verified after transfer. A failed restore is recorded and its output is left for inspection. Failure to load any configured plan aborts before writing because source/repository exclusions cannot otherwise be trusted. Final audit persistence failure returns an error with the job ID and output path rather than reporting success; any completed output remains available for inspection. Request cancellation is recorded as cancelled when the restore returns an error.

## Security boundary

Loopback IP binding only; strict Host and Origin checks; bearer token on every API; cross-site Fetch requests denied; no CORS grants; CSP and frame protection; request body limits. The startup URL passes the token in a URL fragment and the UI removes it immediately, retaining it in sessionStorage. Service metadata and tokens are private user files. This protects against unrelated websites, not untrusted code already running as the same macOS user. Directory browsing is intentionally allowed across the filesystem for an authenticated user and remains subject to macOS permissions.

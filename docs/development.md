# Development and validation

Requirements: Go 1.26.4+, Node 22.12+ or 24+, npm, macOS, executable rsync. Native FSEvents builds use cgo and Apple Command Line Tools; CGO_ENABLED=0 is supported with polling fallback. System openrsync works for basic backups. Homebrew rsync 3.x is detected first when installed; this project never installs system tools automatically.

`make build` installs locked frontend dependencies, typechecks/builds the UI, embeds assets and builds bin/localbackup. `make run` and the root `.command` use project `.data` and 127.0.0.1:18787. `make dev` uses the same isolated data/port and Vite at 127.0.0.1:5173. The packaged app uses ~/Library/Application Support/LocalBackup and prefers 8787; an occupied port falls back to a free loopback port. Development and installed data, tokens, and endpoints are separate. Use only generated source/target fixtures for development; port/data isolation does not isolate writes if both instances are deliberately configured to the same real backup directories. Development prints a Vite URL with the same fragment token. Development origins are accepted only with `-dev`.

`make test` runs Go unit/integration tests with the race detector. `make check` runs go vet and the frontend build. `npm run format:check --prefix apps/web` checks frontend formatting.

The tests use isolated temporary source/target directories and real rsync. They verify two-source isolation, rule agreement, rename reuse, move+modify fallback, metadata change isolation, old-snapshot integrity after deletion/modification, failure/cancellation without publication, unusual NUL-delimited filenames, symlink handling, wrong-volume rejection, recursive path rejection, authentication/Origin/Host protection, API backup→history→restore→retention, SQLite reopen/migrations and interrupted/orphaned snapshot recovery. Native adapter tests also exercise real macOS change delivery and journal replay. Scheduler tests cover durable cursor/dirty-path commits, events arriving during backups, selected-event filtering, dropped-event full-content recovery with unchanged metadata, and private service-directory exclusion. Mode tests also cover nondeleting incremental views, protected mirror scopes, file/directory conflicts, fresh/expired/reused/stale approval handling, scheduled confirmation holds, cross-process repository locks and current-generation cleanup protection. They do not write personal documents or real backup disks.

Browser acceptance was performed with real files under `.data/ui-fixtures`: create a paused two-source plan, preview filters excluding scratch.tmp, inspect planned additions, execute, browse the committed manifest, restore one file to a new directory and verify byte equality. The sample plan is explicitly labeled as an acceptance example and remains paused. Sample sources now live in .demo outside the private service data directory; previous history stays in the original target repository.

`make package` produces an ad-hoc-signed release/Foldsnap.app and zip for the current architecture. Open the .app to start the native menu-bar launcher, service, and browser. Reopen opens the existing UI; startup/child errors are shown in an alert with a sanitized error log under ~/Library/Logs/LocalBackup. A private service-endpoint.json records the actual port; a second CLI process authenticates that exact endpoint before reopening it. A background launchd service is attached rather than duplicated; quitting an attached menu does not stop launchd. `python3 packaging/macos/install-agent.py` explicitly installs the app under ~/Applications and a per-user launchd service. `--uninstall` unloads/removes the agent while preserving backups and data. Do not invoke installation merely to build/test the project.

Default service data: ~/Library/Application Support/LocalBackup. Override with `-data /absolute/path`. Production frontend assets are embedded. `-web apps/web/dist` overrides them for development. `-addr` accepts loopback IPs only.

Browser acceptance for 0.3 additionally created paused generated-data incremental/mirror plans under .demo/modes, verified retention of a deleted incremental source file, inspected/search-filtered file and empty-directory mirror removals, confirmed the start button was disabled until explicit consent, executed the approved run and compared both current views against their original immutable history. All acceptance plans remain paused.


0.15.1 startup acceptance on the local Mac reproduced the previous silent Finder launch failure: the development process occupied 8787 while the installed app used a different database but the same port. Development launch commands now use 18787 and project .data. The native launcher and Go service have distinct executable names, including on case-insensitive volumes. Acceptance exercised Finder double-click, authenticated duplicate service attachment, fallback while 8787 was occupied, concurrent development/production databases (7 vs 0 plans), a simulated child failure with a visible redacted alert, and graceful native termination of both processes followed by a fresh Finder launch. The final service was left running at 8787 with the production database; development services were stopped. Results and the actual Chrome UI screenshot are in .data/startup-acceptance-0.15.1.json and .data/app-launch-0.15.1.png. This verifies the local app launch flow, not Apple notarization or launch on a clean Mac.


Packaging accepts an optional output directory, e.g. `./packaging/macos/package.sh .data/package-next`. It refuses to overwrite a currently running app bundle. Build and validate a separate bundle, wait for the installed service to be idle, preserve the existing data directory, quit the app, then replace the bundle and reopen. Browser/transfer acceptance remains isolated at 18787 and never runs personal plans. 0.16 UI acceptance records are documented in background-scans.md.
